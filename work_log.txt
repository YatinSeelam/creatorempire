2026-09-01 — the scheduler's 200mb was a number storage never agreed to

michael dropped a 57mb cut into the scheduler and got "that file is too large" under a label reading "mp4 up to 200mb". both numbers were ours and neither was true. supabase enforces a project-wide upload ceiling in FRONT of every bucket, and a bucket's own file_size_limit only ever narrows it further, never widens it. `autopost` is set to 200mb; this project's ceiling is 50mb, so the storage api refuses anything over 50mb and answers "The object exceeded the maximum allowed size", which lib/storage-upload.ts turns into "that file is too large". measured against the live project, not guessed: 50 mib uploads 200, 52 mib comes back 413 EntityTooLarge. every clip in the autopost bucket today is under 9mb, which is why nobody hit it until now.

so the ceiling lives in one place, lib/upload-limits.ts, read from NEXT_PUBLIC_MAX_UPLOAD_MB and defaulting to 50 because 50 is the truth on this project. the composer's label, the client side size check in lib/autopost/upload.ts, the 413 message in lib/storage-upload.ts and portfolio's video cap all read that one value now, so they cannot drift apart again. portfolio was promising 60mb, which was ten over what storage would take; capBytes() clamps a per-feature cap to whatever storage will actually accept.

this makes the app honest, it does not make 57mb upload. the only thing that does is raising the ceiling in supabase (storage > settings > upload file size limit), which past 50mb needs a paid plan on the project. after that it is one env var here: NEXT_PUBLIC_MAX_UPLOAD_MB=200 and the label, the check and the error all move together.

2026-08-27 — the invite was a dead address, and the token was the only key

two bugs, one screen. copying an invite gave out
`http://creator-empire.localhost:3000/join/<token>`, and the person it was sent
to, signing in normally on the host this app actually serves, was told they were
not on the roster.

the address
- lib/org.ts `tenantHost()` had a branch above the TENANT_SUBDOMAINS_LIVE check
  that turned any localhost request into `<slug>.localhost:<port>`, on the
  theory that every browser resolves the whole .localhost tld to the loopback
  so it costs nothing. it costs the sign-in. this deploy does no host lookup at
  all and the supabase auth cookie is host-only here (cookie-domain.ts never
  widens on localhost), so the link was a second origin: the login it bounces
  through writes its pkce verifier there, supabase sends the code back to the
  site url instead because that subdomain is not on the redirect allow list,
  and the callback reads for a verifier that was never written on the host it
  is running on. that is the whole of "that sign-in did not finish in this
  browser".
- so: one workspace, one host, in dev as in production. new `originFor(host)`
  mints on the host that asked, `inviteLink()` uses it, `tenantHost()` falls
  through to the request host, and `hasOwnHost()` stops claiming localhost is
  the org's own address. `schemeFor()` is the one place that decides http vs
  https now, instead of two copies of the same startsWith check.

the key
- `accept_org_invite(p_token)` was the only path that could seat anybody from a
  session, and that is not an accident: `authenticated` holds no insert grant on
  org_members, and the select policy on org_invites needs an owner or admin
  seat, so an invited person cannot even read the row that names them. all of
  that is right. what was wrong is that a secret in a url was load bearing.
- new `public.claim_org_invite()`, migration 20260827020000. no arguments, so
  there is nothing for a caller to lie about: it takes the email off auth.users
  for `auth.uid()`, requires it confirmed, finds the newest pending unexpired
  invite written to it, seats them and stamps accepted_at. security definer for
  exactly the reason the token version is. execute revoked from anon, which
  needed saying twice — supabase's default privileges grant it directly, so
  `revoke from public` does not touch it.
- called in three places, all through `claimPendingInvite()` in
  lib/invite-claim.ts, all best effort: the auth callback right after the
  exchange (the ordinary sign-in), `requireViewer()` on the step before it
  redirects to /account (the case where the invite is written while they are
  already signed in — `load()` is cached for that request so the answer is a
  redirect, and the next request reads the seat), and /account itself, so a
  reload collects it. the copy there said "sign in again" and now says "reload
  this page", which is what actually works.
